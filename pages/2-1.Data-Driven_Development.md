
# 코드 중심 개발의 확산

초기의 콘솔 게임과 컴퓨터 게임은 대부분 매우 제한된 하드웨어 환경에서 개발되었습니다.  
메모리와 저장 공간이 극도로 부족했기 때문에, 개발자들은 제한된 자원을 최대한 효율적으로 재사용해야 했습니다. 자연스럽게 게임의 다양한 요소들은 데이터 형태로 분리되어 관리되었고, 하나의 로직을 여러 데이터에 재사용하는 방식이 널리 사용되었습니다.

하지만 시간이 지나면서 PC와 콘솔의 성능은 급격히 발전하게 되었고, 개발자들은 이전보다 훨씬 자유롭게 코드를 작성할 수 있게 되었습니다.

특히 C++ 와 객체 지향 프로그래밍(Object-Oriented Programming)의 확산은 게임 개발 방식에도 큰 변화를 가져왔습니다. 
게임의 다양한 요소들을 클래스와 객체 중심으로 설계하는 방식이 역시 보편화되기 시작했습니다.

이러한 객체 지향 기반 구조는 기능을 빠르게 개발하고 관리하는 데 매우 효과적이었습니다. 소규모 프로젝트나 기능 중심의 개발에서도 코드 중심 구조가 직관적이었고, 기능을 빠르게 구현하기에도 적합했습니다. 그래서 많은 게임 프로젝트들이 객체와 클래스 중심의 Code-Oriented 구조를 적극적으로 채택하게 되었습니다.

하지만 프로젝트의 규모가 점점 커지고 콘텐츠의 양이 증가하면서, 데이터와 로직이 강하게 결합된 코드 중심 구조는 점차 새로운 문제를 만들어내기 시작했습니다.

# 데이터와 로직이 강하게 결합되어 있다면?


![](../assets/Pasted%20image%2020260517231508.png)

만약 오래된 액션 RPG 프로젝트에 새롭게 합류했다고 가정해봅시다.
그리고 그 프로젝트는 수년 동안 기능이 계속 추가되면서 비효율적으로 코드와 시스템들이 복잡하게 얽혀 있는 상태입니다.

이 상황에서 여러분이 만약 캐릭터에 신규 스킬을 추가하는 작업을 맡았다고 상상해봅시다.

- 우선 신규 스킬을 위한 버튼을 연결하기 위해 입력 시스템에서 코드를 수정해야 했습니다.
  이를 위해 ENUM 기반의 새로운 값을 추가했습니다.

- 이제 입력을 추가하자 UI에서 스킬 아이콘이 표시되지 않습니다. 
  확인해보니 UI 시스템에서는 스킬 ID를 하드코딩으로 관리하는 시스템이 존재했고, 여기에 새로 추가한 스킬의 ID를 추가해야 했습니다.

- 스킬에 UI 아이콘이 추가되었지만, 스킬의 효과는 아직 적용되지 않았습니다. 
  스킬의 효과를 적용하기 위해서 스킬 시스템에서 새로 추가한 스킬에 대한 코드를 작성해야 했습니다.

- 이번에는 스킬의 애니메이션이 추가되지 않았습니다. 
  애니메이션 시스템에서 새로 추가한 스킬에 대한 애니메이션과 이에 대한 상태값을 추가해야 했습니다.

- 스킬의 데미지 처리도 추가해야 했습니다. 
  데미지 시스템에서 새로 추가한 스킬에 대한 데미지 계산 코드를 따로 작성해야 했습니다.

결국 단순히 스킬 하나 추가하는 작업이 끝없이 이어지는 시스템의 수정 작업으로 변하게 됩니다.

더 큰 문제는 이런 구조에서는 문제가 발생해도 어디에서 문제가 발생했는지 추적하기 어렵다는 것입니다. 또한 게임의 콘텐츠를 수정하는 작업이 곧 코드 수정으로 이어지고, 작은 수정 하나가 예상하지 못한 버그를 계속 만들어내게 됩니다.

그리고 프로젝트 규모가 커질수록 개발자들은 새로운 기능을 만드는 시간보다, 기존 구조를 이해하고 사이드 이펙트를 막는 데 더 많은 시간을 사용하게 되었습니다.
